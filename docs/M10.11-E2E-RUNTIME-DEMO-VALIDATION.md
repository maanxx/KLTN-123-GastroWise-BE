## 1. Verified Service Topology (Phase A)

Inspected directly from `docker-compose.yml`, `nginx/nginx.conf`, service `Dockerfile`s, and runtime health controllers:

| Service | Container Name | Runtime / Image | Host Port | Internal Port | Health Endpoint | Depends On | Local Database / User |
|---|---|---|---|---|---|---|---|
| **Nginx API Gateway** | `gastrowise-nginx-gateway` | `nginx:1.27-alpine` | `0.0.0.0:8080` | `8080/tcp` | `GET /health` (`200`) | `core-service` (`service_healthy`), `planning-service` (`service_healthy`) | None (reverse proxy) |
| **Core Service** | `gastrowise-core-service` | `node:24-alpine` (NestJS) | Not exposed | `3001/tcp` | `GET /health`, `GET /health/ready` | `mongo-test` (`service_healthy`) | `gastro_core_test` (`CORE_DB_USER`) |
| **Planning Service** | `gastrowise-planning-service` | `node:24-alpine` (NestJS) | Not exposed | `3003/tcp` | `GET /health`, `GET /health/ready` | `mongo-test` (`service_healthy`), `core-service` (`service_healthy`) | `gastro_planning_test` (`PLANNING_DB_USER`) |
| **AI Service** | `gastrowise-ai-service` | `python:3.12-slim` (FastAPI) | Not exposed | `5000/tcp` | `GET /` (`DATA_READY`) | `mongo-test` (`service_healthy`) | `gastro_core_test` read-only (`AI_DB_USER`) |
| **Local MongoDB** | `gastrowise-mongo-test` | `mongo:7.0` (`--auth --bind_ip_all`) | Not exposed | `27017/tcp` | `mongosh` admin `ping` + `CORE_DB_USER` check | None | Persistent volume `mongo_test_data` |

### Inter-Service Routing & Isolation Summary
- **External Ingress:** Clients (Web, Mobile, Demo `curl`, Smoke Test) only enter through Nginx Gateway at `http://127.0.0.1:8080`.
- **Gateway Routing (`nginx/nginx.conf`):**
  - `GET /health` -> Nginx JSON health probe
  - `/api/v1/itineraries*` (and rewrite `/itineraries*`) -> `http://planning-service:3003`
  - `/api/v1/auth*` -> `http://core-service:3001` (strict `5r/s` rate limit)
  - `/api/v1/*` (and legacy rewrites `/restaurants*`, `/dishes*`, `/recommendations*`, etc.) -> `http://core-service:3001`
  - Injects and echoes `X-Correlation-Id` and whitelisted localhost CORS headers.
- **Internal Mesh Auth:**
  - `planning-service` -> `core-service` (`/api/v1/internal/*`) uses `X-Internal-Service-Key` (fails closed with `401` on missing/invalid key).
  - `core-service` & `planning-service` -> `ai-service` (`POST /recommend`, `POST /weather-recommend`, `POST /copilot/message`) use `X-Internal-AI-Key` (fails closed with `401`/`403` on missing/mismatched key, with deterministic fallback on Core Service).
- **Database Ownership Isolation:**
  - `core-service` owns `gastro_core_test` (`readWrite`) and is **Unauthorized** on `gastro_planning_test`.
  - `planning-service` owns `gastro_planning_test` (`readWrite`) and is **Unauthorized** on `gastro_core_test`.
  - `ai-service` has **read-only** access (`read`) on `gastro_core_test`.
  - `docker-compose.yml` explicitly clears `CORE_MONGODB_URI`, `MONGODB_URI_CORE`, `PLANNING_MONGODB_URI`, `MONGODB_URI_PLANNING`, and `MONGODB_URI` so containers can never inherit a host Atlas URI.


## 5. Starting the Local Database

Start `mongo-test` first so `docker/mongo/01-init-users.js` initializes SCRAM-SHA-256 least-privilege accounts on first boot (existing `mongo_test_data` volume is preserved across restarts):

```bash
docker compose --env-file .env.docker.local up -d --wait mongo-test
```

If you need to seed or refresh local demo food data into `gastro_core_test` using the M10.7 pipeline, follow `docs/ingestion/` with local MongoDB credentials only (never Atlas). In the verified local validation dataset, `gastro_core_test` contains 3 open HCMC restaurants (`Phở Hòa Pasteur`, `Bánh Mì Huynh Hoa`, `Cơm Tấm Ba Ghiền`) and 6 available dishes (2 vegetarian).

## 6. Building & Starting All Backend Services

Build the NestJS backend images (and AI image if first run) and bring up the full 5-container stack using `--env-file .env.docker.local`:

```bash
# Build images
docker compose --env-file .env.docker.local build core-service planning-service

# Start all services and wait for healthy status
docker compose --env-file .env.docker.local up -d --wait
```

> **Important:** Always pass `--env-file .env.docker.local` to every `docker compose` command so all containers share the exact same `INTERNAL_SERVICE_KEY` and `INTERNAL_AI_KEY`. If you rotate any key in `.env.docker.local`, run `docker compose --env-file .env.docker.local up -d --wait` (without restricting to a subset of services) so `core-service`, `planning-service`, and `ai-service` all recreate with matching keys.

## 8. Executing the Reproducible E2E Smoke Test Suite

The repository includes a zero-dependency Node.js 24 smoke-test runner at `scripts/e2e/smoke-test.mjs` wired to `package.json`:

### Mode A — Gateway HTTP Smoke Suite (Host Only)
Verifies Nginx Gateway health, restaurant & dish catalog endpoints, legacy gateway rewrites, food recommendations, input validation (`400`), and Planning Gateway auth routing (`401`):
```bash
npm run test:e2e:smoke
```

### Mode B — Full E2E + Internal Docker Mesh & DB Isolation Suite (Recommended)
Adds internal container readiness checks (`core-service:3001/health/ready`, `planning-service:3003/health/ready`, `ai-service:5000/`), `planning-service -> core-service` `X-Internal-Service-Key` enforcement (`noKey=401`, `badKey=401`, `validKey=200`), and bidirectional MongoDB SCRAM DB isolation (`Core -> Planning = Unauthorized`, `Planning -> Core = Unauthorized`):
```bash
SMOKE_CHECK_DOCKER=true npm run test:e2e:smoke
```

### Built-In Local-Only Safety Guards
`scripts/e2e/smoke-test.mjs` refuses to run (exits with code `1`) if:
- `SMOKE_BASE_URL` points to any host other than `127.0.0.1`, `localhost`, or `::1`.
- Any of `MONGODB_URI`, `MONGODB_URI_CORE`, or `MONGODB_URI_PLANNING` contains `mongodb+srv://` or `mongodb.net`.

## 9. Example API Requests & Observed Responses

All examples below target the local Nginx Gateway (`http://127.0.0.1:8080`) and match the verified DTOs in `docs/api/M10_10_FRONTEND_INTEGRATION_GUIDE.md`.

### 1. Gateway Health
```bash
curl -sS "http://127.0.0.1:8080/health"
```
Expected `HTTP 200`:
```json
{"status":"UP","gateway":"nginx-api-gateway","timestamp":"2026-11-28T17:27:38+00:00"}
```

### 2. Paginated Restaurant Catalog (with Correlation ID)
```bash
curl -sS -i -H "X-Correlation-Id: demo-req-001" \
  "http://127.0.0.1:8080/api/v1/restaurants?page=1&limit=10"
```
Expected `HTTP 200` (with echoed `X-Correlation-Id: demo-req-001` header and no `ingestionBatchId`/`ingestionPostDigest`):
```json
{
  "data": [
    {
      "id": "6b0a8f389e583fdd0ef73e27",
      "tenQuan": "Phở Hòa Pasteur",
      "diaChi": "260C Pasteur, Phường Võ Thị Sáu, Quận 3, TP. HCM",
      "status": "open"
    }
  ],
  "meta": { "page": 1, "limit": 10, "total": 3, "totalPages": 1 }
}
```

### 3. Dishes Sorted Ascending by Price (and Legacy Rewrite)
```bash
curl -sS "http://127.0.0.1:8080/api/v1/dishes?page=1&limit=10&sortBy=price&order=asc"
curl -sS "http://127.0.0.1:8080/dishes?page=1&limit=2"
```
Expected `HTTP 200`: `data` sorted ascending by numeric `price` (`10000` VND upwards), valid `meta`, and zero `sourceMetadata` / `externalSourceId` leakage.

### 4. Food Recommendations (Hybrid AI + Deterministic Fallback)
```bash
curl -sS "http://127.0.0.1:8080/api/v1/recommendations/food?keyword=Ph%E1%BB%9F&latitude=10.785&longitude=106.688&radiusKm=5&maxBudget=100000"
```
Expected `HTTP 200` when `ai-service` is reachable and `INTERNAL_AI_KEY` matches:
- `meta.strategy`: `"hybrid"` (automatically degrades gracefully to `"deterministic"` if `ai-service` is down/unreachable or rejects auth).
- Each item contains `restaurant`, `recommendedDishes` (within `<= 100000` VND and without nested bogus `restaurant` stubs), `score`, `reasons`, and `distanceKm`.

### 5. Vegetarian + Budget Recommendation Filter
```bash
curl -sS "http://127.0.0.1:8080/api/v1/recommendations/food?isVegetarian=true&maxBudget=60000"
```
Expected `HTTP 200`: returns only restaurants with available vegetarian dishes priced `<= 60000` VND (2 matches in local dataset).

### 6. Validation Error Handling (`HTTP 400`)
```bash
curl -sS -w "\nHTTP %{http_code}\n" "http://127.0.0.1:8080/api/v1/recommendations/food?latitude=0&longitude=0"
curl -sS -w "\nHTTP %{http_code}\n" "http://127.0.0.1:8080/api/v1/recommendations/food?minBudget=100000&maxBudget=50000"
```
Expected `HTTP 400` Bad Request with clear validation message.

### 7. Planning Service Gateway Auth Guard (`HTTP 401`)
```bash
curl -sS -w "\nHTTP %{http_code}\n" "http://127.0.0.1:8080/api/v1/itineraries"
```
Expected `HTTP 401` (`Unauthorized`), confirming Nginx routes `/api/v1/itineraries` to `planning-service` and JWT protection is active.

## 10. Troubleshooting Common Local Runtime Issues

| Symptom | Root Cause | Safe Resolution |
|---|---|---|
| `required variable MONGODB_ROOT_USERNAME is missing` | Ran `docker compose` without `--env-file .env.docker.local` or missing var in file | Always pass `--env-file .env.docker.local` and ensure all required keys from Section 4 are populated. |
| Core logs `AI recommendation signal unavailable ... status code 403` and `strategy=deterministic` | `gastrowise-ai-service` is running with a stale `INTERNAL_AI_KEY` from an earlier startup | Recreate `ai-service` with the same env file: `docker compose --env-file .env.docker.local up -d --wait ai-service`. |
| `nginx -s reload` does not pick up edited `nginx/nginx.conf` on macOS Docker Desktop | Atomic file writes change the host inode of a single-file bind mount | Recreate only the gateway container: `docker compose --env-file .env.docker.local up -d --force-recreate --no-deps nginx-gateway`. |
| Port `8080` bind error on startup | Another host process is already bound to `8080` | Stop the conflicting local process before starting `nginx-gateway`. |
| `GET /api/v1/restaurants` returns `total: 0` | Fresh local `mongo_test_data` volume with no seeded documents | Run the M10.7 local food ingestion pipeline against local `gastro_core_test` (never Atlas). |

## 11. Stopping Services Safely (Without Deleting Volumes)

To pause services while keeping containers and `mongo_test_data`:
```bash
docker compose --env-file .env.docker.local stop
```

To stop and remove containers/network while **preserving** the `mongo_test_data` volume:
```bash
docker compose --env-file .env.docker.local down
```

> **NEVER RUN `docker compose down -v`** — the `-v` flag deletes `mongo_test_data` and destroys all local test users and ingested restaurant/dish records.

## 12. Known Limitations

1. **Small Local Seed Dataset:** The current local `gastro_core_test` dataset contains 3 HCMC restaurants and 6 dishes from M10.7 sample ingestion; full-scale ShopeeFood datasets can be imported via the existing M10.7 local ingestion pipeline when preparing expanded demos.
2. **Authenticated Planning Write Flow:** Full `POST /api/v1/itineraries/generate` requires a valid signed user JWT; the automated smoke test intentionally performs read-only HTTP checks (verifying Gateway -> Planning `401` JWT guard and `planning-service -> core-service` `X-Internal-Service-Key` candidate fetch `200` without mutating test databases).
3. **External OAuth / SMTP / Gemini Keys:** Local Docker validation uses local placeholders for Google OAuth, SMTP, and Gemini keys; external third-party OAuth login or outbound email OTP sending is out of scope for offline local Docker demos.
4. **Remote GitHub Actions CI:** Local validation verifies TypeScript compilation, NestJS builds, all 289 unit/contract tests, Python syntax checks, and Docker E2E smoke tests locally; remote GitHub Actions status is verified only after pushing to GitHub.
